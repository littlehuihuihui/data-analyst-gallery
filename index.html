>_ 分析框架速览

① 问题拆解框架

业务问题 → 口径定义 → 数据诊断 → 根因定位 → 方案推动 → 效果验证 → 机制固化

② 常用分析模型

  • 漏斗分析：用户生命周期（开户→激活→活跃）+ 行为（开机→点播→播放）+ 订购（浏览→下单→支付→开通）
  • 分层分析：用户价值金字塔 + R×F×M + 告警分级
  • 同期群分析：按批次对比；首批用户到期流失高峰约第13个月
  • 对比分析：对照组评估策略（一键登录优化前后）
  • 行为占比分析：播放次数/时长占比构建内容偏好
  • 流失预估：优惠到期、仅开机一次、沉默月份数三类特征分层

③ 口径定义原则

从业务定义出发 → 找到数据源 → 验证质量 → 统一标准 → 固化为看板指标。入职初期梳理数据字典与埋点文档，明确核心字段定义、来源与关联。

④ 数据血缘追溯

利用字典与埋点文档梳理核心业务线数据链路：

能力体现：异常时判断归属（采集/加工/应用/定义）；上游变更预判下游；交叉验证发现隐患；变更时同步更新范围。典型案例：华为40万→加工层同步链路；0播放时长→采集层埋点+路径；220万→口径定义层。

⑤ 数据资产沉淀

爱立信：原始告警表上建 issue-record-tracking；5字段组合唯一键；每日增量比对四状态（新增/持续/待观察/已解决），告警全生命周期闭环。状态机与 OTT 用户状态表（新增激活/持续活跃/沉默/流失）底层方法论一致。

银河OTT：8 个 Datart 看板替代人工取数、数据字典可查口径、三方关联框架复用；陪产假前客服查询上线 BI，团队免 SQL 自助，休假业务未受影响。

⑥ 协作模式

与运营分工：数据挖掘与异常定位（数据侧）+ 策略与报告（运营侧），共同完成用户质量、活跃度等报告。

220万虚假用户 · 口径对齐与真实活跃率

场景还原：刚入职时，移动质疑运营能力——400万用户、活跃仅约40万；银河后台激活设备约180万。两队口径不一，无人能说清差异。

> 思维路径

  1. 抛出问题：400万 vs 180万，活跃率无法确定

  5. 落地：合规下不能批量销户，优惠到期逐步处理，对外解释为正常流失

0播放时长 · 双重根因诊断

场景：后台有用户进入点播产品线但播放时长为 0。需要定位是用户没看，还是数据没上报。

> 思维路径

步骤1：漏斗拆解
开机用户 → 进入 Launcher 界面 → 点击模块 → 跳转对应界面 → 播放 / 未播放

步骤2：定位根因一（产品逻辑层）
Launcher 界面中不同模块行为不同——部分模块进入后自动拉起播放，部分不自动拉起。进入不自动拉起的模块时，用户停留在界面但未触发播放，播放时长为 0。

步骤3：定位根因二（数据采集层）
即使用户触发了播放，若播放后断网或关机，结束日志未上报到后台，播放时长同样会被记为 0。

> 根因总结

  • 根因一：Launcher 模块的自动拉起机制不一致，属于产品逻辑问题
  • 根因二：播放结束日志在异常退出时丢失，属于埋点采集问题

> 影响

两个根因叠加，使「播放时长为 0」的用户占比偏高，影响活跃指标准确性，也影响后续合作方关于「按有播放用户结算」口径的讨论。

三方数据打通 · CRM / 设备库 / APK

新业务线吸收机顶盒教训，推动 CRM、设备库、APK 三方标识统一（手机/SN/MAC）。

过程：历时约 5 个月，在无明确负责人、多方推诿与资源受限的情况下，仍逐项推动各方打通接口链路。

> 三方数据详情

数据源唯一标识存储内容
CRM（移动）手机号用户信息（开户、套餐、优惠等）
设备库（杭研）SN码设备信息、设备基础软件功能使用情况（闹钟、日历等）
APK（银河）MAC地址用户播放行为、屏幕点击行为

> 打通逻辑

  • CRM ↔ 设备库：通过手机号与 SN 码的绑定关系关联
  • 设备库 ↔ APK：通过 SN 码与 MAC 地址的设备映射关联
  • 最终目标：一个用户（手机号）→ 一台设备（SN码）→ 所有行为（MAC地址）的全链路打通
  • 统一用户标识为 SN 码

> 数据血缘追溯：统一标识落地过程

1. 发现问题：APK 业务表无 SN 字段 → 追溯采集表（日志表），SN 字段位置存在但数据为空 → 追溯 PB 日志，确认该字段未做埋点。

2. 治本方案：提需求更新 APK 版本 → 新增 SN 码埋点 → 数据自动存入采集表 → 再提需求将 SN 码从采集表写入业务表 → 校验数据准确性。

3. 兜底方案：沉默用户未更新 APK 版本，SN 码仍为空。通过三方映射反向补全——移动提供手机号+SN码、杭研提供 SN 码+MAC、银河提供 MAC+手机号，三表联查能关联的补全、无法关联的标记为未知。

4. 方法论沉淀：后续新业务线可提前确定统一标识、提前检查各表关联字段是否完备，从源头避免此类问题。

这部分是数据血缘能力在数据工程中的完整体现——从应用层异常追溯到采集层根因，推动技术侧修复，并设计兜底方案覆盖无法修复的历史数据。

> 可量化结果

自动化关联替代手工对账 · 效率约+90% · 支持设备套现预警
